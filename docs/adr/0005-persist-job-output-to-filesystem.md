# 5. Persist job output to a filesystem log store

Date: 2026-09-27

## Status

Proposed

## Context

Atlantis streams the output of every plan, apply, and workflow hook to the job
page at `/jobs/<job-id>`. That output lives only in process memory, in
`AsyncProjectCommandOutputHandler`:

- **Memory is unbounded.** Every line of every job, for every open pull
  request, is held until the pull request is closed or merged. Pull requests
  stay open for days or weeks, and there is no per-job cap.
- **Nothing survives a restart.** A restart, redeploy, or crash loses every
  job log. Job links already posted in pull request comments and commit
  statuses then fail with `invalid key`, and there is no record of what a past
  apply printed ([#6137](https://github.com/runatlantis/atlantis/issues/6137),
  [#6022](https://github.com/runatlantis/atlantis/issues/6022)).
- **Workflow hook output is never cleaned up.** Hook jobs are keyed by the pull
  request alone, and the pull request close path only cleans up per-project
  jobs, as noted in review of
  [#5359](https://github.com/runatlantis/atlantis/pull/5359).

Capping the in-memory buffer alone does not help: a cap either drops the start
of a long log or its end, and either way output is lost.

Prior attempts:

- [#2157](https://github.com/runatlantis/atlantis/pull/2157) persisted job
  logs to S3. It was closed after its author stopped responding; maintainers
  said a revival with an interface for other storage backends would be
  welcome.
- [#6176](https://github.com/runatlantis/atlantis/pull/6176) (open) persists
  each job's complete output to the coordination database when the job ends,
  as part of a web UI rewrite.

The store and backend model proposed in
[#6694](https://github.com/runatlantis/atlantis/issues/6694) and
[#6829](https://github.com/runatlantis/atlantis/pull/6829) names a `jobs` store,
bound today to `memory`, and requires each new store and backend pair to define
its behavior and namespace layout. This ADR defines the `jobs` store on a
`filesystem` backend.

## Decision

Atlantis will persist job output to local files through a `LogStore`
interface, and serve jobs that are no longer in memory from those files.

### Write path

Every output line is written through to the store as it is produced, alongside
the in-memory buffer, not in bulk when the job ends. A crash mid-apply keeps
everything printed up to that point. When a job completes, its file is synced
to disk and closed.

The in-memory buffer keeps serving live viewers. Persistence never reads from
it, so a later cap on the buffer does not limit what is persisted.

### Layout

Files live under `--job-log-dir`, which defaults to `<data-dir>/job-logs`:

```text
<job-log-dir>/<url-escaped repo full name>/<pull number>/<job id>.log
```

- One directory per pull request, so its logs can be deleted in one step.
- The repository full name is URL path escaped into a single segment, so
  GitLab subgroups and similar names cannot create extra levels or leave the
  root.
- Files hold plain text, one output line per line, and are created with mode
  `0600` in directories with mode `0700`.
- Job IDs are UUIDs generated by Atlantis. The read path takes them from the
  request URL, so any ID that is not UUID-shaped is rejected before touching
  the filesystem.

This layout is a compatibility requirement once released.

### Read path

The job page and its websocket first look in memory. A job that is not there,
for example after a restart, is replayed from its file and the stream is then
closed. A job with no file is registered for live output as before, so opening
a job page before its first line still works.

### Lifecycle

A pull request's job logs are deleted when it is closed or merged, at the same
point its in-memory state is cleaned up today. Cleanup is driven by the pull
status in the coordination store, so it also covers jobs from before a
restart. The pull request close path also runs one pull-level cleanup, which
removes workflow hook output from memory and disk.

Logs are not retained after the pull request closes. Age-based retention is
left for a later decision.

### Multiple replicas

Each job's file has a single writer: the replica running the job. When all
replicas set `--job-log-dir` to the same shared or network volume, any replica
can replay a job another replica ran, and closing a pull request removes its
logs for all of them. The volume must support appending to an existing file.
NFS, Amazon EFS, and Azure Files do. Mountpoint for Amazon S3 does not support
appends in general-purpose buckets.

Live tailing of a job running on another replica is out of scope. Such a job
shows the output written so far.

### Alternatives considered

- **Store output in the coordination database**, as in #6176. Rejected.
  Writing the whole output when the job ends loses it when the process dies
  mid-job, which is the case an audit trail matters most for. Large plan and
  apply outputs grow BoltDB, and for Redis users they move the logs back into
  memory.
- **Write directly to object storage.** Deferred. S3 objects cannot be
  appended to, so a driver must write chunk objects and reassemble them on
  read. That fits better as an `s3` backend for the `jobs` store once #6829
  lands, behind the same `LogStore` interface.
- **Cap the in-memory buffer without persistence.** Rejected, because every
  truncation policy loses output.
- **Make persistence opt-in.** Rejected. Disk use is bounded by open pull
  requests, the same bound memory has today, and a restart losing every job
  log is the behavior users report as a bug. Installations that disable log
  streaming, such as TFE remote execution, write nothing.

## Consequences

- Job pages and their links keep working across restarts until the pull
  request closes.
- The full log is on disk, so a follow-up can cap the in-memory buffer to what
  live viewers need and replay the rest from disk, bounding memory without
  losing output.
- New default behavior: installations with log streaming enabled write job
  output under `--data-dir`. Disk use grows with the output of open pull
  requests.
- If a pull request's close event is never received, its logs remain on disk
  until removed by hand. A later retention decision can add age-based cleanup.
- The jobs index on the main page still lists only jobs in memory. Past jobs
  are reached through their links until the index can be rebuilt from stored
  metadata.
- A shared volume without append support fails writes, which are logged as
  warnings, while the jobs themselves continue.
- If #6829 is accepted, `--job-log-dir` maps to the `filesystem` backend root
  for the `jobs` store and follows its namespace rule,
  `<configured-root>/<store-id>/...`. Aligning before release may rename the
  default directory from `job-logs` to `jobs`.
